From a split vote to an approved rule: how Rulebook finds what a guideline is missing, and how I checked whether it helped.

When labelers disagree, the disagreement is the signal.

Three small local models read the same receipt and sometimes give three different answers. A majority vote settles each word and moves on. A split vote says something a count hides: the guideline never told the models what to do.

These words come from the cluster that became rule 1.7, which covers truncated item names.

Turn the split into a rule.

Rulebook clusters the disagreements and hands them to agents. An orchestrator picks which clusters to work on and says why, a diagnoser finds the cause, and a rule writer drafts one numbered rule with examples. The agent harness is written from scratch in Python, with no agent framework.

Everything runs offline on one consumer GPU through Ollama, one model loaded at a time.

Name the cause before writing a rule.

Not every disagreement is the guideline’s fault. Some are OCR misreads, some are one model’s mistake, and some are text that is truly unclear. Only a real gap in the guideline produces a rule.

Prices like 12.500 or Rp 2.000,00 are parsed by code, never by a model.

A verifier that admits it is noisy.

Each draft rule is tested by code on a 30-receipt gold set, against a control rule that changes nothing. Rule 3.9 lifted gold-set accuracy from 0.593 to 0.630 while the control moved it to 0.588. But the control alone swung single labelers by several points, so the verdict is advice, not a gate.

A human sees the numbers and decides.

A human decides, and the loop waits.

Applying a rule and relabeling the data are approval-gated tools. The run stops until someone approves, edits or rejects the rule in the review UI. Only an approval creates a new guideline version.

The decisions table records who decided what, and when.

Every step is on the record.

Every model call, tool call and orchestrator decision lands in a trace you can browse in the UI, with the reason the orchestrator gave. The answer key stays locked away: agents, tools, prompts and skills never see the evaluation labels, and a test enforces it.

Only the eval scripts read the answer key, after a run finishes.

Did it generalize? Not quite.

Rules 3.8, 1.7 and 3.9 came from receipts 50 to 69. To test them on receipts the loop never saw, the same labelers labeled 50 new receipts under guideline v1 and v4. The pass bar was set before the run.

Agreement and review share improved, and every labeler improved, but majority-vote accuracy rose 1.5 points against a 2-point bar. That is a fail. No tuning followed, and it is one run per version.

What it still cannot see.

The loop only looks at disagreements, so a mistake all three models share never forms a cluster. OCR text costs accuracy, the verifier is noisy, and the runs are small.

The full limitations and next steps are in the repository README.
