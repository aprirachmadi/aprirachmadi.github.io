A casual report can hide an urgent incident.

A ticket’s tone is a poor guide to its severity. “Is that bad??” might describe a password entered on a suspicious site. Dispatch reads the original issue alongside company context and prepares an assessment for a technician to check.

The example is security_casual, a synthetic case from the selected evaluation run.

Give the model something to work from.

MCP tools gather the ticket and company details, then retrieve similar resolved tickets. The workflow makes separate model calls for classification and drafting, so a technician can inspect the assessment as well as the wording.

The selected run exercised the real read-only workflow against isolated synthetic PSA fixtures. Its history was retrieved, rather than simply taken from each case’s preselected context.

Approval belongs to the reviewed revision.

Preview lets a technician inspect the model workflow. Apply runs generation again and saves the classification, linked assessment and an unsent draft. The technician can edit the saved text before approving it.

Edits and approval check the current revision. A stale revision gets a conflict response. Approval records review; it never sends a message.

A correct label is only half the job.

For the credential-exposure example, all four labels matched the reference: security, urgent, immediate, and a raised security flag. The draft still needed review. Its correctness/safety judge score was 0.7 out of 1.

The judge noted the missing instruction to stop using the suspicious link and unclear technician escalation. This example scored below the provisional 0.8 threshold.

Measure the labels. Then read the drafts.

The selected run generated predictions and drafts for all 40 synthetic cases. All four classification fields matched on 33 cases. Priority was the weakest individual field: 35 of 40 matched, and one of nine urgent cases was missed.

Gemma4:12b generated the output. DeepEval GEval used orvix/deepseek-v4.1-flash to judge the drafts. Langfuse recorded the experiment. Scores describe this run, not production reliability.

Keep the source beside the response.

The technician workbench brings the queue, original issue, saved assessment and editable draft into one view. Attention flags make review needs visible. Run history, weekly reporting and audit views help inspect what the system did.

A local demo with an explicit boundary.

Dispatch demonstrates triage and review on synthetic IT scenarios. It has no authentication or public deployment, and it does not send replies, close tickets or perform remediation. The next step toward a production service would require evidence and controls beyond this demo.

The 40-case run does not establish performance on real client tickets. No time-saved, latency, adoption or business-impact result is available.

Run configuration, scoring and limitations

Evaluation set: dispatch/triage, 40 of 40 cases, no subset. Dataset SHA-256: 003ddbd7f444ecd9ec07dfaba10bd5920088d7ca44773ab646d3c25cba109cd8.

Generation: gemma4:12b, prompt triage-v1. Draft judge: DeepEval GEval with orvix/deepseek-v4.1-flash, rubric draft-geval-v1. Both draft metrics assessed all 40 outputs. The provisional 0.8 threshold is uncalibrated; correctness/safety passed on 34/40 drafts, consistency on 40/40.

Definitions: exact match requires category, priority, urgency and security flag to all match. Security-flag recall measures flagged reference cases; it is distinct from security-category accuracy. Judge scores assess draft wording, not real-world incident resolution.

Artifact: data/evals-af9f2eef-b336-4253-a6a9-c9474bdcd2a6.json. Its summary scope text is stale: top-level mode and evaluation mode identify MCP evaluation, corroborated by the evaluation implementation. The run uses retrieved fixture context, not real customer tickets or a production PSA.

Interpretation: one run on a small synthetic set. No claim of production reliability or measured time savings. The screenshot predates this run and demonstrates the interface only.
